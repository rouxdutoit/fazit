# Plan 02-08: classify roster service plans, part 1 (names 0 to 9 and A to E)

## Goal

Licence data can only say which areas an organisation pays for when every service plan in its products is assigned to an area or explicitly to none. This data plan classifies the first half of the plans that no one has classified yet, by hand, following the existing entries.

<objective>
Built on the report redesign merged into main (D-91) and on plans 02-04 and 02-07. Task 1 checks both and stops if either is missing.

Tasks 1 and 2 classify the unclassified roster plans whose canonical name starts with a digit or A to C, then D to E. Task 3 checks the result, the unchanged demo and writes the review table.

Purpose: D-123 ("every service plan in the roster gets an explicit area or `null` by hand"). The split into two plans follows the orchestrator's rule that the classification is split if one run cannot carry it; plan 02-09 classifies F to Z and adds the coverage test of D-110.
Output: one new entry in `service_plans.yaml` for every unclassified roster plan from 0 to 9 and A to E (297 on the 2026-11-22 copy; a newer roster may hold more or fewer), regenerated site demo reports (checksum line only), a SUMMARY review table.

Run order of the phase: 02-00 and 02-01 (wave 1); 02-02 (wave 2); 02-03 and 02-04 (wave 3); 02-05 (wave 4); 02-06 and 02-07 (wave 5); then one plan per wave: 02-08, 02-09, 02-10, 02-11, 02-12, 02-13, 02-14 (waves 6 to 12).
</objective>

Rules for every entry:
1. Same plan family, same area: a plan whose name differs from a hand-made one only by a tier, a suffix (`_GOV`, `_EDU`, `_FACULTY`, `_STUDENT`, `_E3`, `_P1`, `_NEW`) or a market variant takes that entry's area.
2. Decide by what the plan delivers, using its friendly name and the products that include it (the worksheet). A Dataverse plan inside a Dynamics product is `power_platform` (precedent `DYN365_CDS_P2`); a Dynamics application plan is `null`.
3. `null` only when the plan's function lies outside every area in the table. When a plan could belong to an area or to `null`, choose the area: hiding a dependency would make an area look more ready than it is. When it could belong to two areas, choose the one whose function it mainly delivers and mark it "uncertain" in the SUMMARY.
4. Use only the area ids of the table (`windows_software` and `licences` are not used for plans, as in the hand-made entries).
5. Entry format, exactly as the existing ones: `  - {name: <canonical roster name>, guid: <lower-case GUID>, workload: <area id or null>}`; put the name in double quotes when it contains anything other than letters, digits and underscores; insert each entry at its place in the existing order (by name without regard to case, then by GUID). Add no note (a note would be a new string for both locales).
6. Change no hand-made product entry and no existing plan entry.
